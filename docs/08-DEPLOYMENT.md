# 08 — Deploying (demo first, then production)

The step-by-step for putting the app online. [04-LAUNCH-ROADMAP.md](04-LAUNCH-ROADMAP.md)
covers *what* has to be true before real data goes in; this covers *how*.

---

## The shape: one service, one URL

```
  phone / laptop ──https──►  Render web service  ──►  Neon PostgreSQL
                             (Express: /api/* + the React app)
```

The API and the React build are served **by the same Node process**
(`SERVE_CLIENT=true`). That is deliberate:

- The refresh cookie is `SameSite=Lax` and must be **first-party**. One origin
  means no proxy, no CORS, and no "logged out on every reload".
- The earlier plan (Cloudflare Pages proxying `/api/*` to Render via
  `_redirects`) **does not work**: Cloudflare Pages only proxies relative paths
  on the same site, never an external domain.
- One thing to deploy, one set of logs, one URL to give the station.

| Piece | Service | Cost |
| --- | --- | --- |
| App (API + web) | Render web service, Frankfurt | Free (sleeps after 15 min) → $7/mo `starter` to stay awake |
| Database | Neon, region Frankfurt | Free, 0.5 GB, backups included |
| Email (demo) | A Gmail account + App Password | Free, ~500 emails/day |
| Email (production) | Brevo or Resend with your own domain | Free tier |

## Step 1 — Email with Gmail (demo)

Gmail works well for a demo. For production, move to Brevo/Resend on a domain
you own (see "Before production" below).

1. Sign in to the Gmail account that will **send** the emails.
2. Turn on **2-Step Verification**: <https://myaccount.google.com/security>
3. Create an **App Password**: <https://myaccount.google.com/apppasswords>.
   Name it "LRC 401" and copy the 16 characters (you can ignore the spaces).
   Your normal Google password will **not** work over SMTP.
4. The values:

```env
EMAIL_TRANSPORT=smtp
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=the-sending-address@gmail.com
SMTP_PASS=abcdefghijklmnop           # the App Password, no spaces
EMAIL_FROM="LRC Saida 401 <the-sending-address@gmail.com>"
```

`EMAIL_FROM` must be the same Gmail address. Gmail rewrites any other sender.

5. Test it locally before deploying. Put those values in `server/.env`, then:

```powershell
npm --prefix server run email:test -- you@example.com
```

It signs in first and tells you plainly if the App Password is wrong. Check spam
too: mail from a fresh Gmail sender often lands there for the first few sends.

### What this app emails

- **Invitations.** This is the only way people join.
- **Password reset links**, from "Forgot password".
- **"Your password was changed"** security notices.

**The 2FA codes are not emailed.** Two-factor authentication uses an
authenticator app (Google Authenticator, Microsoft Authenticator, 1Password…)
with a QR code. That is deliberate: a code sent to the same inbox as the
password reset would not be a second factor.

## Step 2 — Database (Neon)

1. <https://neon.tech> → New project → region **Frankfurt** (AWS eu-central-1).
2. Create a database named `lrc401`.
3. **Connection details** → untick "Pooled connection" → copy the **direct**
   string. It ends in `?sslmode=require`.
4. Create the tables and seed from your machine (PowerShell):

```powershell
$env:DATABASE_URL = "postgresql://...neon.tech/lrc401?sslmode=require"
$env:SEED_SUPERADMIN_EMAIL = "you@example.com"          # your real address
$env:SEED_SUPERADMIN_PASSWORD = "A-long-Password-2026"    # 10+ chars, upper, lower, digit
$env:SEED_SUPERADMIN_NAME = "Your Name"

npm --prefix server run db:deploy     # applies migrations; never resets
npm --prefix server run db:seed       # roles, teams, vehicles, items, forms, the super admin

Remove-Item Env:DATABASE_URL, Env:SEED_SUPERADMIN_PASSWORD
```

Seeding with your **real** address from the start means the default
`admin@lrc401.local` account never exists online.

## Step 3 — The app (Render)

1. Push the branch you want to deploy (for the demo, `staging`):
   ```powershell
   git checkout staging; git merge dev; git push; git checkout dev
   ```
2. <https://render.com> → **New → Blueprint** → connect the GitHub repository.
   Render reads [`render.yaml`](../render.yaml) and creates a service called `lrc401`.
3. Render asks for the values marked `sync: false`:

| Variable | Value |
| --- | --- |
| `CLIENT_URL` | `https://lrc401.onrender.com`, the service's own URL. If the name is taken, Render shows the real one; put that here. |
| `DATABASE_URL` | the Neon direct string from step 2 |
| `TOTP_ENC_KEY` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. **Save a copy.** |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `EMAIL_FROM` | from step 1 |

The three JWT secrets are generated by Render automatically.

4. Deploy. The first build takes about 3 minutes. The server **refuses to
   start** if a secret is missing or weak, if `CLIENT_URL` is not https, or if
   email is left on `console`. Its log names the exact variable to fix.

> If `CLIENT_URL` is wrong, the app loads but sign-in fails with "Origin not
> allowed", and invitation links point to the wrong place. It must match the
> address in the browser bar exactly, with no trailing slash.

## Step 4 — Check it works

- [ ] `https://<your-app>.onrender.com/api/health` shows `"status":"ok"`
- [ ] Sign in with the super admin from step 2
- [ ] **Reload the page and you stay signed in.** This proves the cookie works.
- [ ] Invite yourself at a second address; the email arrives and the link opens the app
- [ ] Enrol 2FA on your phone, sign out, sign back in with a code
- [ ] File one report on a phone over mobile data, in English and Arabic

## The admin password

Passwords are stored as one-way bcrypt hashes, so **no one can look one up**:
not you, not the database. They can only be **reset**:

```powershell
# Locally:
npm --prefix server run set-password -- admin@lrc401.local 'New-Password-2026'

# Against the online database:
$env:DATABASE_URL = "postgresql://...neon..."
npm --prefix server run set-password -- you@example.com 'New-Password-2026'
Remove-Item Env:DATABASE_URL
```

The new password must meet the policy (10+ characters with an uppercase letter,
a lowercase letter and a digit). The command also clears any lockout and signs
out every existing session. From inside the app, a super admin can reset anyone
else's password from **Users**, and anyone can use **Forgot password** once
email is working.

## Before production (after the demo)

- [ ] **Email from a domain you own** (Brevo/Resend) with SPF + DKIM. Gmail is
      fine for a demo but caps sending, and mail from a personal address looks
      like phishing to volunteers and to spam filters.
- [ ] **Render `starter` plan** ($7/mo) so the first person at 07:00 does not
      wait 40 seconds for it to wake.
- [ ] A **separate** Render service and Neon database for `production`, with
      fresh secrets and a new `TOTP_ENC_KEY` (see [07](07-BRANCHES-AND-DEPLOYMENT.md)).
- [ ] Test a Neon restore once.
- [ ] Custom domain: Render → Settings → Custom Domains. Then update `CLIENT_URL`.

## Before every deploy

```powershell
npm start                                  # terminal 1
npm --prefix server test                   # terminal 2: smoke + scenarios + security
npm run lint
```

`npm --prefix server run test:security` on its own runs only the attack suite:
forged tokens, foreign origins, mass assignment, privilege escalation, path
traversal, hostile query strings on every list, and hostile bodies on every
write endpoint. Its rule is simple: **nothing may return a 5xx**.
